### WP-01.6 Invalid HTML in `index.html` meta tags

- [x] `index.html:18-23` use typographic quotes: `name=”twitter:card”` instead of `name="twitter:card"`

**Corrections to the findings above, from doing the work:**

- **`multi.html` was not a clean reference.** Its meta tags were right, but it had the *same*
  two structural defects. Copying its meta block across fixes only the first bullet.
- **The quotes were functionally broken, not cosmetic.** A `”` is not an attribute delimiter, so
  the parser reads the attribute *name* as `”twitter:card”`. Verified before the fix:
  `[...document.querySelectorAll('meta[name]')]` returned `”twitter:card”` with the smart
  quotes included, so no valid Twitter card metadata existed at all. After: `twitter:card`.
- **`<h1>` directly inside `<a>` is fine.** `<a>` has a transparent content model, so it may
  contain flow content. Only the intervening `<span>` was wrong, since `<span>` accepts
  phrasing content only. The fix removes the `<span>` rather than moving the `<h1>` out of the
  anchor.
- **`fw-bold` on that span was dead CSS.** Bootstrap sets `h1 { font-weight: 500 }`, which beat
  the inherited bold, so the heading rendered at 500. Moving `fw-bold` onto the `<h1>` made it
  live and jumped the weight to 700. Dropped it instead, to keep the rendering identical —
  worth knowing that `fw-bold` was never doing anything here.
- **Moving `container-fluid` is visible.** The nav loses its horizontal padding and the inner
  collapse div gains it, so the brand and heading shift 12px left and the nav grows ~12px
  taller (measured: nav 1232×88 → 1141×100, brand y 31 → 15). Everything else is pixel-stable,
  and the heading outline is unchanged. Revert just that bullet if the old spacing is wanted.

Verified after the change, per PHP version: 12/12 browser checks (module loads, opcode dump,
ordinary run, line numbers, no side effects), heading outline identical, `h1` no longer inside
a `span`, and all four Twitter meta names parsing correctly.

### WP-01.7 `print` / `printErr` handlers drop blank lines

- [x] **Corrected finding.** An earlier version of this file claimed the handlers
      "inject spurious newlines". That was **wrong**. Emscripten's TTY layer emits
      `print`/`printErr` once per line with the newline already stripped, so joining
      the calls with `'\n'` is **correct** and reconstructs the original text exactly
- [x] The real defect was the guard: both handlers started with `if (!data) return;`,
      which **discards empty lines**
- [x] **Fixed** in `playground.js` and `multi-run.js` — the guard is now
      `data === undefined || data === null`
- [ ] Add a unit test for a payload containing blank lines

### WP-01.8 `?>` prefix breaks `declare(strict_types=1)`

- [x] `playground.js:94` / `multi-run.js:89` wrap user code as `?>${code}`
- [x] This makes `declare()` not the first statement (readme "Todo" item, still open)
- [x] Pass user code unmodified; only prepend `?>` when the code does not start with `<?php`
- [x] Verify `__FILE__`, `__LINE__` and `declare(ticks=1)` also behave

**The `?>` was load-bearing, not a mistake.** `phpw_run()` compiles through
`zend_eval_string()`, which expects code **without** an opening tag. Passing
`<?php …` unmodified fails outright (`rc=1`). So `?>` closed eval_string's implicit PHP
mode and the user's own `<?php` reopened it. Every example, and `hello_world.php`, is a
complete `<?php` script, so the convention is unambiguous — and the trick is exactly what
broke `declare()`.

Measured before, with `?>` + code:

```
?><?php declare(strict_types=1); echo "B";   -> rc=1, "strict_types declaration must be
                                               the very first statement in the script"
?>echo "C";   (no opening tag)              -> rc=0, output ""   <- silently nothing
?><?php echo __FILE__;                      -> "script"
```

**Fix:** stage the editor contents as a real file in MEMFS and run it with `phpw()` —
the same mechanism `getOpcodes()` already uses. A file needs no tag translation, and it
puts the run path and the dump path on the same footing, which is what WP-13.9 asked for
before the Opcodes tab shipped. `phpw_run()` and its `?>` wrapper are now unused by the
playground.

Verified in Chromium, 8/8:

- `declare(strict_types=1)` accepted, and typed args are enforced
- no stray `?>` ahead of the program's own output
- `__LINE__` is exact — no offset
- `__FILE__` is now `/run/script.php`, a real path, rather than the literal `script`
- `declare(ticks=1)` works (the trailing tick is PHP's own shutdown tick, correct)
- `hello_world.php` runs; still 12/12 browser checks on 8.4.26 and 8.5.11; `multi.html`
  runs `extensions.php` correctly through the same change

**Side effect, and a pre-existing gap it exposed.** A syntax error was previously
invisible: `phpw_run()` reported `rc=1` with `lastError` `"parse error in script"` but
wrote nothing to stdout *or* stderr, so the user saw no message at all. `phpw()` does
emit it — but on **stdout**, because the embed SAPI sends compile errors to its output
layer:

```
Parse error: syntax error, unexpected token "{", expecting variable in /run/script.php on line 1
```

So syntax errors are now shown for the first time, but they land in the **Output** panel
while the Errors panel says "No Errors!". Moving them across needs either a bridge-side
`ub_write`/error-output split or a heuristic in `runPHP` (on a failed run, treat captured
stdout as the error). Not done here — out of scope for this item, and it needs a
decision about which stream PHP's own errors belong on.

### WP-01.9 Version-switch handler has no error path

- [x] `playground.js:807-810` — `phpVersionDropdown` change handler is `async` with no `try/catch`
- [x] A failing module load leaves an unhandled rejection and no user feedback
- [x] `multi-run.js` is better here (it wraps `runCode`); align the two

**Reproduced before fixing.** Driving a `change` to a version with no module, with the Errors
panel and badge read out of the DOM afterwards:

```
selectedVersion: "9.9.9"      <- control left on the version that failed
errorsPanel:     "No Errors!"  <- actively wrong
errorBadgeHidden: true
unhandled page error: Error: PHP execution failed: Failed to fetch dynamically
                     imported module: .../php-9.9.9-web.mjs
```

The Run button and auto-run already had `try/catch` → `handlePhpRunError()`; only the version
handler did not. Worse than the missing message was the cascade: those two paths read
`uiElements.phpVersionDropdown` rather than the event target, so once the dropdown sat on a
broken version **every** later run failed too, until the user noticed and picked again by hand.

**Fix:** wrap the handler in `try/catch` → `handlePhpRunError(err)`, then put the dropdown back
on a version that can load. Successes are recorded from the Run button, auto-run and the
version handler alike.

Two details worth keeping:

- The state is a dropdown option value, **not** `php.version`. That getter returns
  `phpversion()`, i.e. `"8.4.26-dev"` for a development build, which matches no option.
- The fallback is the first option with a non-empty value, **not** `options[0]`.
  `loadPhpVersions()` puts a "Select a PHP version" placeholder with an empty value first, so
  `options[0].value` is `""` and an `options[0]` fallback silently does nothing.

**After, both the warm and the cold path** (with and without a prior successful run): error
shown, badge lit, dropdown back on `8.5.11`, **0 unhandled rejections**, and the next Run
succeeds. Still 12/12 browser checks on 8.4.26 and 8.5.11.

**Not done — `multi-run.js` shares the stuck-selection gap.** Its `runCode()` has
`try/catch`/`finally` and surfaces `err.message` to `#errorElement`, so it was never missing
an error path, but a failed version select also stays selected there and poisons subsequent
runs the same way. Applying the same revert to `MultiRunPanel` would align them; left alone
here to keep this item to `playground.js`.

### WP-13.2 The readme's blocker is a false one

The readme claims *"activating the extension is not possible during runtime, because one
can't set PHP_SYSTEM_INI directives"*. Three findings invalidate that:

1. **VLD installs its hooks in `PHP_RINIT`, not `MINIT`.** `vld` reads `VLD_G(active)`
   and installs `zend_compile_file` / `zend_compile_string` on **every request init**.
   The bridge already runs `php_request_startup()` once per run, so a setting changed
   between runs takes effect on the next run. **No module restart is needed.**
2. **VLD hooks `zend_compile_string`, not just `zend_compile_file`.** `phpw_run()`
   uses `zend_eval_string()` (`php-wasm-bridge.c:572`), which goes through
   `zend_compile_string`. So **eval'd code is dumped too** — we do not need to switch
   the run path to a temp file via `phpw()`.
3. **[VERIFIED] `zend_alter_ini_entry_chars()` can modify a `PHP_INI_SYSTEM` entry after
   startup.** Confirmed against `php-src` `PHP-8.4`, `Zend/zend_ini.c:356`:

   ```c
   modifiable = ini_entry->modifiable;
   modified   = ini_entry->modified;

   if (stage == ZEND_INI_STAGE_ACTIVATE && modify_type == ZEND_INI_SYSTEM) {
       ini_entry->modifiable = ZEND_INI_SYSTEM;   /* explicit special case */
   }

   if (!force_change) {
       if (!(ini_entry->modifiable & modify_type)) {
           return FAILURE;
       }
   }
   ```

   php-src deliberately lowers `modifiable` for exactly this stage/modify_type pair.
   Corroborated by `php_ini_activate_per_dir_config()` in `main/php_ini.c`, which calls
   `php_ini_activate_config(..., PHP_INI_SYSTEM, PHP_INI_STAGE_ACTIVATE)`.
   **The readme's blocker is definitively false.**

   - [ ] **Caveat:** that special case assigns `ini_entry->modifiable` and **never restores
         it**. Harmless for the four VLD entries (all already `PHP_INI_SYSTEM`), but never
         call this on an entry that is `PHP_INI_ALL`, or it is silently downgraded.
   - [ ] The field is `modifiable`, not `modifiability` (easy to get wrong when reading).
   - [ ] The entry must already exist in `EG(ini_directives)`, i.e. **module startup must
         have run** — see the `phpw_init()` bug in WP-13.4

**Consequence: no baked-in `php.ini`, no `PHPRC`/`PHP_INI_SCAN_DIR` env dance, no
second module build, no restart. All INI handling stays inside the bridge.**

### WP-13.3 VLD already writes to stderr — no patching, no file reading

Verified against `derickr/vld` @ `0.19.1`, `vld.c` and `srm_oparray.c`:

- **Every opcode dump goes to `stderr`.** All output flows through
  `int vld_printf(FILE *stream, …)`, and every call site passes `stderr` —
  `vld_dump_op()`, `vld_dump_znode()`, `vld_dump_zval*()`, `vld_dump_oparray()`,
  `vld_dump_fe()`, `vld_dump_cle()`.
- **The only file VLD writes is `paths.dot`**, opened in `PHP_RINIT` under
  `if (VLD_G(save_paths))`, and `vld.save_paths` **defaults to `0`**.
- **The `<save_dir>/<md5>.<checksum>.dump` scheme no longer exists.** That was legacy
  VLD (≤ 0.13). `vld.save_dir` survives in the INI table but is now used only for
  `paths.dot`.
- C `stderr` in Emscripten is routed to the JS **`printErr`** callback, which
  `playground.js:80-84` already collects into `#buffer_stderr`.

**Therefore: no VLD patch is needed, and no filesystem access is needed** (beyond writing
the snippet, which `FS` already supports — `Dockerfile:252` exports
`EXPORTED_RUNTIME_METHODS='["ccall", "UTF8ToString", "lengthBytesUTF8", "FS", "HEAPU8"]'`).

The real problem is the opposite of the one first assumed: the dump is **mixed into the
same stderr buffer as PHP warnings, notices and fatal errors**, and the playground renders
that buffer into the *Errors* panel (`uiElements.output_error`). So the work is
**separation**, not retrieval.

- [x] **Separation is achieved by never executing the code.** With `vld.active=1` and
      `vld.execute=0`, RINIT installs a no-op `zend_execute_ex` (`{ /* nothing */ }`), so the
      snippet is compiled and dumped but never run. **No runtime diagnostic can enter the
      stream**, and the Output/Errors panels are untouched.
- [x] **The dump is purely static.** In `vld_dump_op()` the `E`/`I`/`O` markers come from
      `vld_analyse_oparray()` (static branch analysis), not from execution. So a compile-only
      dump is **identical** to what a real run would emit — no information is lost.
- [ ] Keep `vld.save_paths=0` so no `paths.dot` is written to MEMFS

### WP-13.4 Bridge work — CHOSEN: Design 1 (minimal C, JS orchestration)

**Decision:** Design 1, no VLD patch. Rationale and maintenance trade-offs in WP-13.5.

**C: one new export, `phpw_vld_config(active, execute, verbosity, dump_paths)`.** Four
`zend_alter_ini_entry_chars(..., PHP_INI_SYSTEM, PHP_INI_STAGE_ACTIVATE)` calls, verified
in WP-13.2. **Implemented** in `src/php-wasm-bridge.c`, with `_phpw_vld_config` added to
`EXPORTED_FUNCTIONS` in both Dockerfiles and in `build-tools/scripts/test-bridge.sh`.

**JS orchestration — implemented** as `PHP.getOpcodes(code, verbosity)` in
`playground/assets/js/playground.js`:
write snippet to `/vld/code.php`; `phpw_vld_config(1, 0, verbosity, 1)`; swap `printErr`;
`ccall('phpw', null, ['string'], ['/vld/code.php'])`; restore `printErr` in `finally`;
`phpw_vld_config(0, 1, 1, 1)`; `FS.unlink`.

**Smoke test — implemented** as section 16 of `test/php-wasm-bridge.test.mjs`, skipped
automatically when the module has no VLD. It asserts the dump names the script, contains
`INIT_FCALL` and `ECHO`, that a snippet with a `file_put_contents()` side effect **does not
execute**, that a normal run afterwards is not dumped, and that 50 consecutive dumps all
succeed and leave the module working.

Why this design and not the alternatives:

- [x] Reuses the **already-exported** `_phpw` — no new file-reading C, no `opendir`/`unlink`
- [x] Reuses the already-exported `FS` — no build change needed for filesystem access
- [x] No `open_memstream` / `dup2` / `fileno` POSIX surface
- [x] Avoids `zend_compile_string` entirely — no function-pointer dispatch trap, and no
      cross-version return-type risk. (`zend_compile_string` is a **pointer**; calling
      `compile_string()` directly would silently bypass VLD's hook and yield no dump.)
- [x] No `destroy_op_array()` lifecycle to get right
- [x] Zero re-application cost on a VLD bump (WP-13.5)

Rejected alternatives, recorded so they are not re-proposed:

- [ ] **Prefix-split heuristic** — `vld.active=1` plus a normal `phpw_run()`, then split
      stderr at the first `PHP Warning|...` line. No C at all, but **fragile**: a warning
      inside a string literal, or a user `error_log()` call, splits the dump wrongly. It also
      feeds the dump into `parsePhpError()`, whose fallback regex
      `/parse error|syntax error|fatal error|unexpected/i` would fire on uppercase opcode
      names and produce spurious editor error markers. **Rejected.**
- [ ] **`dup2`/`tmpfile` around a full run** — same filtering problem as above, with more C.
      Dominated.
- [ ] **Patch VLD: configurable stream** — under-specified. `vld_printf()` takes a `FILE*`;
      an INI string cannot become one without the extension opening it, which reintroduces
      the unpredictable-filename problem. **Rejected as incoherent.**
- [ ] **Patch VLD: `vld_dump(string $code): string`** — the technically cleanest fix: it
      could call `vld_dump_oparray()` directly so `vld.active` never needs to be `1` and no
      INI manipulation is required at all. Kept as an **optional upstream PR**, never a
      dependency. See WP-13.5.

#### WP-13.4.1 Bugs found in review (all fixed in the implementation)

- [x] **Bug 1 — `verbosity` is not a boolean.** `vld.verbosity` is `OnUpdateLong` (0-3), so
      `char buf[2] = {v ? '1' : '0'}` silently turns a request for 3 into 1 with no error.
      Fixed with `phpw_vld_int_str()` using `snprintf("%d")`, plus a 0-3 range check that
      returns `PHPW_ERROR`.
- [x] **Bug 2 — no `phpw_init()` before touching INI, causing silent failure.**
      `zend_alter_ini_entry_ex()` looks the entry up in `EG(ini_directives)`, populated only
      by `php_embed_init()`. `phpw_vld_config()` runs before `phpw()`, so on a cold module
      all four lookups return `NULL` and the dump came back **empty with no visible cause**.
      Fixed: `phpw_vld_config()` now calls the idempotent `phpw_init()` first, and JS turns
      a non-zero return into a thrown error carrying `phpw_last_error()`.
- [x] **Bug 3 — `FS` was not reachable.** `playground.js` destructured only `ccall` from the
      module. Fixed: the resolved module namespace is kept in `PHP.#module`.
- [x] **Re-entrancy guard.** `phpw_vld_config()` refuses while a request is active.
- [x] **Parse errors are raised, not rendered.** `getOpcodes()` checks `phpw`'s return status
      and throws `phpw_last_error()` instead of returning error text as if it were opcodes.
- [x] **`printErr` restore is safe.** Restored only when the captured original was a function,
      so a module created without one does not get `undefined` assigned.
- [x] **`FS.mkdir` EEXIST** is caught rather than aborting the dump; the directory is
      deliberately kept between runs.
- [ ] `fs.analyzePath()` avoided in production code in favour of `try`/`catch` around
      `FS.mkdir` (the *test* uses it, where the version is pinned)
- [ ] Document that the dump shows `filename: /vld/code.php`, and that this path uses a real
      file (no `?>` prefix) so **line numbers are exact** (WP-13.9). Nobody should "restore"
      the prefix.
- [ ] **Open:** confirm `Module.printErr` reassignment actually intercepts. Asserted by the
      new test "a dump is produced", but only once the module can be built.
- [ ] **Open:** cap the dump and report truncation visibly (VLD emits no length of its own)

### WP-13.5 VLD patch maintenance — the re-application question

**Decision: no patch.** WP-13.4 explains why. The upstream surface Design 1 depends on is:

1. four INI names — `vld.active`, `vld.execute`, `vld.verbosity`, `vld.dump_paths`
2. "all output goes to C `stderr`"
3. "`vld.execute=0` makes `zend_execute_ex` a no-op"
4. the already-exported `_phpw` and the already-exported `FS`

Items 1-3 have been stable since VLD 0.14. **Bumping `VLD_VERSION` costs nothing but
running the WP-13.7 checks — there is no patch to re-apply.**

For comparison, a patched design would have needed `patches/0001-vld-*.patch` applied with
`git apply --3way` after the clone, anchored on `vld_printf()` (whose signature has been
stable for years, making it the lowest-churn patch point). VLD releases are infrequent
(0.17.2 -> 0.18.0 -> 0.19.0 -> 0.19.1), so that cost is low — but non-zero, and it buys
nothing Design 1 does not already have.

- [ ] **Add a CI job that builds with `ENABLE_VLD=1`. Non-negotiable.** Today CI never
      compiles VLD at all (`ENABLE_VLD=0` everywhere), so a bump that breaks the build, breaks
      `--disable-all` + `--enable-vld`, or changes the dump format would go unnoticed until a
      user opens the Opcodes tab. This job converts "we must remember to re-check a
      dependency" into "CI fails and tells us" — and it matters whether or not we patch.
- [ ] Run the WP-13.7 smoke assertions in that job, so an upstream change in output format
      surfaces as a test failure rather than a visual regression
- [ ] Pin `VLD_VERSION` and review the diff on bump; the project is small enough that
      `git log` in the ext dir is a quick sanity check
- [ ] **Optional, non-blocking:** send upstream a PR adding `vld_dump(string $code): string`,
      which would let `vld_dump_oparray()` be called directly and remove the INI
      manipulation entirely. VLD and php-wasm-builder share an author (Derick Rethans), so
      there is an existing relationship. **Send it, but never depend on it.**
- [ ] If it ever lands: feature-detect `function_exists('vld_dump')` and prefer it, keeping
      Design 1 as the fallback. A rejected or delayed PR must never break the playground.

VLD prints a `line` column sourced from `op->lineno`. Design 1 writes the snippet to a

exact by construction. The main run path still uses `?>${code}` + `zend_eval_string()`
